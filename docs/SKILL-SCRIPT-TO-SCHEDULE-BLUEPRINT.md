# 剧本到日程蓝图技能

## 目标

本技能用于把一段自然语言剧本转换为本项目可运行、可保存、可恢复、可验证的对象式日程蓝图。它面向不了解本项目历史上下文的 agent，因此所有关键契约都必须从仓库当前代码和文档确认，不能依赖角色名称、文件名或旧对话记忆推断。

本技能覆盖：

- 从剧本抽取角色、对白、选项、条件、分支和副作用；
- 写入正确的 `data/<lang>/socialXXa/b.json` 或 `workXXa/b.json`；
- 使用注册节点和类型化连接构造蓝图；
- 设计自然、分散且可验证的 `consumeTime` 时间推进；
- 对所有分支进行拓扑、语义和内容完整性验证。

本技能不允许绕过 `ScheduleRunner`、直接调用 `TimeService`、把剧情效果硬编码到应用层，或用“JSON 能解析”代替蓝图验证。

## 适用时机

当用户提供：

- 一段 NPC 对话剧本；
- 多个选项和好感度/怀疑度结果；
- “如果满足某条件”“否则”“第二天再次访问”等剧情条件；
- 需要把内容放入某个日期和阶段的 Social/Work 日程文件；
- 需要让对话消耗游戏时间或限制同晚互动次数；

应加载并执行本技能。

## 必须先读取的资料

在修改前使用 `read_file` 和 `search_files` 读取：

1. `AGENTS.md`：项目边界、时间单位、数据规则、验证要求；
2. `docs/SCHEDULE-BLUEPRINTS.md`：蓝图顶层结构、节点端口、连接方向和运行时语义；
3. `docs/DATA-SCHEMAS.md`：日程文件和条目结构；
4. `js/core/ScheduleNodeRegistry.js`：当前真正注册的节点和端口；
5. `js/core/ScheduleBlueprint.js`：当前校验规则；
6. `js/core/ScheduleRunner.js`：节点执行语义；
7. `js/core/ScheduleValueEvaluator.js`：数值输入和条件求值；
8. 目标语言目录中同类的现有日程文件；
9. 角色 roster（通常是 `data/<lang>/npcs.json` 或实际项目对应文件），确认稳定 `npcId`；
10. 目标文件的所有调用点和加载路径，确认该文件的 `a/b`、日期、phase 和队列含义。

如果文档与代码不一致，以代码的注册表、校验器和运行器为准，并在交付时报告差异；不要自行发明节点类型或端口名称。

## 核心契约

### 日程条目

日程条目的 `id` 是稳定持久化 ID，必须在语言目录加载的全部日程文件中唯一。NPC 必须保存稳定 `npcId`；显示名、头像、立绘路径只属于展示元数据。

Social 条目通常类似：

```json
{
  "id": "social01b_ajie_example",
  "type": "other",
  "npcId": "ajie",
  "name": "阿杰",
  "avatar": "🐶",
  "displayName": "剧情标题",
  "blueprint": {}
}
```

不要把显示名当作 ID，不要因为“前一天已对话”这种自然语言描述就擅自发明不存在的全局变量或完成条件。只有当项目数据契约提供了真实、稳定的条件时，才编码 `prerequisites` 或蓝图条件。

### 蓝图

新蓝图必须使用：

```json
{
  "startNodeId": "start",
  "nodes": {},
  "connections": []
}
```

必须满足：

- `startNodeId` 指向唯一的 `flowStart`；
- 至少有一个 `scheduleEnd`；
- 节点映射键与节点对象的 `id` 相同；
- 流程连接使用 `fromNodeId/fromPort → toNodeId/toPort`；
- 流程端口不能与数值端口混连；
- `choice` 的 `branchCount`、`labelN`、选项连接数量一致；
- 每个可达节点最终都能到达 `scheduleEnd`；
- 不能留下孤立节点、越界选项端口、失效连接或循环；
- 新内容使用对象式蓝图，不把旧 `dialogueTree` 当作新数据模板。

### 副作用

剧本里的状态改变必须映射为注册的操作节点，并通过显式流程连接执行一次：

- NPC 好感度或怀疑度：使用项目规定的 `setGlobal` 或专用注册节点，并确认目标变量 ID；
- 主角属性：使用 `statOperation`；
- 背包：使用 `inventoryOperation`；
- 结局：按项目契约使用 `onShow.ending` 或结束节点效果；
- 时间：使用 `consumeTime`；
- 关键词：使用文本中的规范 `[[keyword_id]]`，只引用 `keywords.json` 中存在的 ID。

不得把新的分支效果塞进已废弃的 `options[].effects` 或未被运行器执行的自定义字段。副作用节点必须位于对应选项出口之后，并能从该出口到达。

## 标准转换流程

### 第 1 步：建立剧本结构表

不要直接从长文本边读边写 JSON。先在内存中建立结构表，每个剧情段至少记录：

| 字段 | 内容 |
| --- | --- |
| 日程 ID | 稳定且全局唯一 |
| 文件 | 例如 `social01b.json` |
| NPC ID | 从 roster 确认的稳定 ID |
| 入口条件 | 仅使用真实存在的条件 |
| 共同对白 | 所有路径都会经过的对白 |
| 选项 | 原始顺序、文字、条件 |
| 分支对白 | 每个选项下的完整对白 |
| 副作用 | 变量、数值、物品、关键词或结局 |
| 汇合点 | 分支何处重新合并 |
| 结束 | 到哪个 `scheduleEnd` |
| 时间目标 | 该日程的平均时间成本 |

保留剧本原文的对白文字、选项顺序和重复语气。不要为了“简化 JSON”删除会影响剧情、关键词或分支识别的对白。

### 第 2 步：检查目标文件并防止重复

使用 `read_file` 读取目标文件完整内容，使用 `search_files` 搜索日程 ID。加载当前 JSON 后按稳定 ID reconcile：

- 已存在且明确要求修改：按 ID 修改；
- 不存在：追加新条目；
- 同一文件已经存在两个同 ID 条目：先消除重复，再继续；
- 不要假定上一次失败的生成没有写入文件；
- 所有文件使用 LF 换行。

完成后，验证当前语言目录以及项目要求扫描的所有语言日程 ID 唯一。节点 ID 只需在**单个蓝图内部**唯一；不同蓝图重复使用 `start`、`end`、`n1` 等节点 ID 是合法的，不能用跨蓝图全局集合误报错误。

### 第 3 步：把对白转换为 text 节点

每一行玩家可见对白建立一个 `text` 节点：

```json
{
  "id": "line_ajie_01",
  "type": "text",
  "inputs": {
    "speaker": "阿杰",
    "text": "你来了。"
  },
  "outputs": {},
  "x": 300,
  "y": 200
}
```

注意：

- `speaker` 和 `text` 放在该节点约定的输入字段；
- 节点必须从 `startNodeId` 可达；
- 玩家对白也要建成 `text` 节点，不要把对白藏在选项标签里；
- 关键词只使用规范 `[[id]]` 标记；
- 坐标服务编辑器展示，不改变运行语义；
- `x=0` 或 `y=0` 是合法坐标，不能用真值判断丢弃。

### 第 4 步：把选项转换为 choice 节点

选项使用动态分支端口：

```json
{
  "id": "choice_main",
  "type": "choice",
  "inputs": {
    "branchCount": 2,
    "label0": "那我相信你。",
    "label1": "还是算了。"
  },
  "options": [
    { "label": "那我相信你。" },
    { "label": "还是算了。" }
  ],
  "outputs": {}
}
```

然后分别连接：

```json
{
  "fromNodeId": "choice_main",
  "fromPort": "option0",
  "toNodeId": "branch_positive",
  "toPort": "flowIn"
}
```

要求：

- 选项顺序和原剧本一致；
- `branchCount` 等于选项数量；
- `label0...labelN-1`、`options` 兼容字段和选项连接不能互相矛盾；
- 条件隐藏选项时保留原始分支索引，不重编号连接；
- 每个选项出口都必须有可达后续流程；
- 选项副作用放在出口之后的操作节点中。

### 第 5 步：编码条件和分支汇合

自然语言条件先归类：

1. 条目入队条件：放在条目 `prerequisites`；
2. 进入某段剧情的条件：使用 `branch`、`segmentBranch` 或节点条件；
3. 某个选项的可见条件：放在该选项支持的条件字段；
4. 运行期间等待状态变化：使用 `waitUntil`，不能自己在应用层轮询；
5. 同一段对白的“高好感/低好感”版本：用真实的好感度来源连接到条件节点，或在数据层拆成有明确条件的条目。

多个分支如果都需要同一效果，应在分支汇合后使用一个公共节点，避免每条路径重复执行。反过来，如果不同分支效果不同，不能过早汇合导致效果丢失。

每个剧情段至少画出以下逻辑图再写 JSON：

```text
flowStart
  → 共同对白
  → choice / branch / segmentBranch
      ├→ 分支 A → 副作用 A ┐
      └→ 分支 B → 副作用 B ┘
  → 共同后续对白或时间节点
  → scheduleEnd
```

### 第 6 步：设计时间成本

时间推进必须通过 `consumeTime` 节点，普通单位是 20 分钟：

```json
{
  "id": "time_03",
  "type": "consumeTime",
  "inputs": { "minutes": 20 },
  "outputs": {}
}
```

#### 设计原则

不要把目标成本写成一个末尾的 `consumeTime(240)`，也不要把 12 个 20 分钟节点连续堆在末尾；连续节点对玩家仍然等价于一次突然跳过大量时间。

也不要把全部时间节点都塞进最前面的共同流程。自然的布局应当贯穿整个对白流程：

- 前段共同对白后有一部分；
- 第一个选项后的分支对白中有一部分；
- 中段继续对白后有一部分；
- 后段对白接近结束但仍有剧情内容时有一部分；
- 最后一句对白之后不要直接接时间节点再到 `scheduleEnd`。

时间节点应放在对白节点之后或合理的剧情动作之后，让玩家看到“聊了一会儿，时间过去 20 分钟”的节奏。不要把时间节点插入会让一句对白在语义上被切断的位置。

#### 分布算法

对每个蓝图：

1. 枚举从 `startNodeId` 到每个 `scheduleEnd` 的可达路径；
2. 收集每条路径上的对白节点和分支结构；
3. 设定目标时间，例如 240 分钟，即约 12 个 20 分钟单位；
4. 按整张图的拓扑/对白顺序选择分布点，而不是只选择共同前缀；
5. 优先每个对白位置最多插入一个时间节点；只有短蓝图不够 12 个位置时，才在少数剧情段安排两个相邻节点；
6. 对不同分支允许小幅浮动，但必须计算每条路径的节点数和平均值；
7. 禁止 `consumeTime → scheduleEnd` 作为最后一跳；
8. 若某条路径明显少于目标，优先在该路径中段增加节点，不要全部补到末尾。

目标不是机械地让每条路径完全相等，而是让玩家体验均匀、各选法平均接近目标。验证时应同时报告：路径数量、最小/最大/平均分钟数、时间节点位置分布。

#### 时间与可用性检查

时间设计必须结合运行时的真实规则：

- `TimeService.advanceBy()` 只接受非负且符合项目单位规则的分钟数；
- 工作窗口、夜间、NPC 睡眠时间和睡眠不足阈值来自当前数据/代码，不要凭感觉计算；
- 如果目标是让同时推进多个 NPC 产生睡眠成本，先计算从下班时间到睡眠结算的真实可用分钟；
- 不要只比较“3 × 单次成本”和睡眠阈值，还要检查 `DormMode`/`SocialApp` 在什么时间会禁止继续互动；
- 若成本使第三个 NPC 根本无法开始，应把它记录为有意的硬约束，不能声称只是软限制；
- 不要使用 `Date`、`getHours()`、浏览器计时器或系统时间控制游戏时间。

### 第 7 步：写入和保持数据

复杂的批量生成或迁移可以在内存中完成，但最终必须通过项目认可的文件写入工具写回，并保留完整 JSON 文档。不要用只输出代码块的方式代替修改。

写入后立即重新读取或解析实际文件，检查：

- 文件仍是合法 JSON；
- 原有条目未被无意删除；
- 新条目 ID 没有重复；
- 每个蓝图节点映射键和 `id` 一致；
- 所有原剧本对白仍存在；
- 关键词 ID 仍然存在；
- 时间节点数量和分钟数符合设计；
- 文件使用 LF。

## 验证工作流

### 静态结构验证

对每个目标文件执行：

1. Python JSON 解析；
2. 文件 LF 检查；
3. 条目 ID 在文件内和项目范围内唯一；
4. 节点键与节点 `id` 一致；
5. 连接两端节点存在；
6. 连接端口存在且类型匹配；
7. `startNodeId` 指向 `flowStart`；
8. 所有节点从起点可达；
9. 所有可达流程路径可到达 `scheduleEnd`；
10. 每个 `choice.branchCount` 与标签/选项/有效分支端口一致；
11. 所有分支副作用节点可达且只执行一次；
12. 所有 `consumeTime.minutes` 为明确的合法值；
13. 不存在末尾直接连接 `scheduleEnd` 的时间节点；
14. 目标时间节点在整个流程中有多个不同的前置对白来源。

### 内容覆盖验证

静态图正确不代表剧本转换正确。建立剧本期望清单并逐项检查：

- 每一行 NPC 对白存在；
- 每一行玩家对白存在；
- 每个选项文字存在且顺序一致；
- 每个“好感度 +5/-5”“怀疑度 +5”等效果都映射到了正确分支；
- 条件高/低分支都存在；
- 白噪音、耳机、游戏、尾款等关键剧情段没有被遗漏；
- 每个分支都能走到结束；
- 不存在只写了标题、但没有剧本内容的占位节点。

可以通过文本字符串和稳定节点 ID 做确定性探针，但不要只检查节点数量；节点数量相等不能证明内容正确。

### 时间分布验证

对每条可达路径计算：

```text
pathMinutes = sum(consumeTime.inputs.minutes)
```

至少报告：

```text
路径数量
最小耗时
最大耗时
平均耗时
每条路径的时间节点数量
末尾时间节点检查
```

推荐验收条件：

- 时间节点都是独立的 20 分钟节点；
- 节点分布在多个对白阶段；
- 末尾不是 `consumeTime → scheduleEnd`；
- 路径耗时落在设计目标的合理范围；
- 分支差异是对白长度导致的可解释浮动，而不是某个分支漏了整段时间成本；
- 若使用 240 分钟目标，平均路径耗时应接近 240 分钟；允许的上下限必须在任务中明确，而不是验证失败后临时放宽。

### 代码验证

如果只修改 JSON，至少执行：

```bash
python3 <确定性 JSON/蓝图验证脚本>
git diff --check
```

如果修改了运行时代码，还要执行相关文件的：

```bash
node --check js/core/ScheduleNodeRegistry.js
node --check js/core/ScheduleBlueprint.js
node --check js/core/ScheduleRunner.js
```

不要主动进行浏览器 UI 验证，除非用户明确要求或给出必须复现的步骤；静态验证和浏览器验证的结论必须分开报告。

## 常见失败模式

### 1. 末尾一个巨大时间节点

症状：整个对话结束时突然跳过 240 分钟。

修复：拆成多个 20 分钟节点，按整条对白图分布；最后一段对白后不要直接进入时间节点再结束。

### 2. 末尾连续多个 20 分钟节点

症状：虽然数值变成多个节点，但玩家仍然看到连续跳时，体验与一次性消耗没有区别。

修复：把这些节点移动到前、中、后多个对白阶段；不要只在末尾补齐。

### 3. 所有时间节点集中在开头共同流程

症状：玩家刚开始聊天就连续推进大量时间，后面的对白又完全不推进。

修复：按全图对白顺序重新分配；共同流程、选项分支后的对白和后续对白都应参与分布。

### 4. 只验证 JSON 解析

症状：文件能解析，但节点不可达、分支断裂、连接引用失效或效果未执行。

修复：执行完整拓扑、端口、分支、内容覆盖和路径耗时验证。

### 5. 把跨蓝图重复节点 ID 当成错误

症状：`start`、`end`、`n1` 在不同蓝图重复，探针错误报告重复 ID。

修复：节点 ID 的唯一范围是单个蓝图；日程条目 ID 才需要在项目规定范围内全局唯一。

### 6. 只给一条分支连到结束

症状：某个选项正常，另一个选项点击后卡住或直接失败。

修复：从每个动态 `optionN` 出口开始单独追踪到 `scheduleEnd`，并验证所有分支副作用。

### 7. 为自然语言条件发明变量

症状：剧本写“昨天已与角色对话”，agent 自行创建不存在的变量或错误使用显示 ID。

修复：先查数据契约；没有真实稳定状态就保留为文件/条目语义，不添加猜测条件。

### 8. 把时间写到应用层

症状：点击 NPC 时直接调用 `timeService.advanceBy()`，导致保存、恢复、队列和蓝图语义不一致。

修复：创建或复用日程实例，让 `ScheduleRunner` 执行 `consumeTime`；应用层只负责入口、展示和实例生命周期。

### 9. 批量生成留下重复条目

症状：`ScheduleData` 预加载时报 `Duplicate schedule id`，整个游戏启动失败。

修复：写入前按稳定 ID reconcile；写入后扫描所有目标日程文件的 ID 唯一性；不要假设失败脚本没有部分写入。

### 10. 把选项效果藏在兼容字段

症状：编辑器能显示效果，但正式运行器不执行。

修复：使用注册的操作节点和明确的流程连接；不要新增未注册的 `effects` 语义。

## 最终交付格式

完成后以中文报告：

1. 修改了哪些文件；
2. 新增/修改了多少日程条目；
3. 剧本中的哪些条件、分支、副作用已映射；
4. 时间节点的设计目标、实际路径最小/最大/平均耗时；
5. 运行了哪些验证命令及真实结果；
6. 尚未验证的内容或已知限制。

不得把未运行的验证写成“通过”，不得用理论上的路径结果代替实际脚本输出，也不得隐瞒验证脚本失败后仍未修复的问题。
